# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

QuickRemote is a presentation/PC remote built as three Dart projects (no workspace tooling; each is built separately):

- `quick_remote_app/`: Flutter mobile client, Android only (there is no `ios/` project).
- `quick_remote_pc/`: Flutter desktop server for Windows (controls PowerPoint and WPS Presentation) and Linux (controls LibreOffice Impress and WPS Presentation).
- `packages/quick_remote_shared/`: pure-Dart package with `RemoteCommands` (command strings, allowlists), referenced by both apps via a `path:` dependency.

`quick_remote_wear/` is the Wear OS watch app, a separate Kotlin + Compose for Wear OS Gradle project (no Flutter). It has no connection of its own: it uses the phone app's connection to the PC (see "Watch app").

`site/` is the promo site (static HTML/CSS/JS, no framework): `index.html` in Turkish and `en/index.html` in English share `style.css`, `main.js` (the live demos; it holds no text, every word is in the HTML) and `assets/`. The two pages are generated from `site/tools/parts/` by `site/tools/build_pages.py` (every sentence is a `{{tr||en}}` pair, icons are Material Symbols Rounded paths in `site/tools/icons/`), so edit a part and run the script, never the pages; `tools/verify.mjs` checks both in a headless browser and `tools/social.mjs` regenerates the share images (`tools/README.md`). The phone, watch and PC pieces on the page copy the apps' components, palettes and strings, so a visible change to those screens may need the same change on the site; features not yet tried on a real device are marked as such there (section "Neyi denedik"). `landing-page/` is the old site and is no longer updated. README and many code comments are in Turkish.

### Android build toolchain (`quick_remote_app/android`)

- Gradle 9.3.1, AGP 9.1.0 and Kotlin 2.4.0 match the Flutter 3.47 template. Flutter's `DependencyVersionChecker` fails the build below Gradle 8.14, AGP 8.11.1 or KGP 2.2.20, and warns below Gradle 9.1, AGP 9.0.1 or KGP 2.3.20. Upgrade these three together, in `gradle/wrapper/gradle-wrapper.properties` and `settings.gradle.kts`.
- Build with a JDK from 17 to 25. Flutter's Java/Gradle table stops at Java 25, so a newer system default (JDK 27) is not supported. Without `flutter config --jdk-dir`, Flutter uses Android Studio's bundled JBR (Java 25 on the Windows machine). Where that is missing, set a JDK 21 with `flutter config --jdk-dir <path>` (e.g. `~/.jdks/jdk-21.0.12.1+1`) and run `./gradlew` with the same `JAVA_HOME`.
- Gradle gets 4 GB (`org.gradle.jvmargs`); 8 GB, the Flutter template's value, made a 16 GB machine page. A first build after a Flutter upgrade downloads the engine jars from `storage.googleapis.com`; if the network drops (e.g. the laptop sleeps) the build fails and Flutter retries, so keep the machine awake. For a quick device check, `flutter build apk --debug --target-platform android-arm64` builds one ABI instead of three.
- Never put `org.gradle.java.home` in the repo's `gradle.properties`, because it is machine-specific. It belongs in `~/.gradle/gradle.properties`.
- `compileSdk = 37` because `permission_handler_android` 14.x needs it. `targetSdk` still follows Flutter (36). The app's Kotlin target uses the `kotlin { compilerOptions { jvmTarget } }` DSL, not `kotlinOptions`.
- `android.builtInKotlin=false` and `android.newDsl=false` in `gradle.properties` must stay. Removing them breaks plugins that still apply KGP (`flutter_background`, `nsd_android`). Remove them only after those plugins migrate to built-in Kotlin, and drop `kotlin-android` from the app at the same time.
- `android.overridePathCheck=true` is required because the repo path contains non-ASCII characters.

Flutter is pinned there (`FLUTTER_VERSION`, keep it equal to the machine's) and in `release.yml`. Third-party actions are pinned to commit SHAs with a `# vX.Y.Z` comment; update both together. ## Architecture

### Wire protocol (mobile ↔ PC)

- The PC runs a TLS WebSocket server (`dart:io HttpServer`, self-signed cert generated on first run and never renewed: phones pin its fingerprint, a new one makes them ask again; it is regenerated only when it cannot be loaded) and advertises `_quickremote._tcp` over mDNS (`nsd` on Windows, Avahi on Linux). The mobile app finds it via mDNS, a QR code, or manual IP entry.
- Auth: the client's first message is `{"auth": PIN, "name": DEVICE_NAME}` (6-digit session PIN, plain inside TLS; the manual-entry dialog enables Connect only at 6 digits). `name` is optional: the phone's user-given name or model, shown in the PC's connected-phones list after `ConnectedClient.sanitizeName`. The server closes unauthenticated sockets after 5 s. `AuthManager` (`services/server/auth_manager.dart`) blocks an IP for 60 s after 5 failures and re-checks that on every attempt, allows at most 3 unauthenticated sockets per IP and 32 in total, and pauses all pairing for 60 s after more than 20 failures within a minute (the PIN is then replaced and the PC UI says so). Limits are counted per `AuthManager.clientKey`: IPv4-mapped addresses as plain IPv4, IPv6 per /64. Upgrade requests carrying an `Origin` header (browsers) are refused.
- Only the local network may connect (`LocalNetwork`, `services/server/local_network.dart`): private, link-local, loopback and CGNAT addresses, or one in the same /24 (IPv4) or /64 (IPv6) as a PC address. The server listens through `TlsHandshakeGate` (`services/server/tls_handshake_gate.dart`) under `HttpServer.listenOn`, not `HttpServer.bindSecure`, which waits for a TLS handshake forever: it refuses other addresses before TLS, gives each handshake 10 s, and allows 8 at once per `clientKey` and 64 in total. It runs the handshake on a `RawSecureSocket` (a `SecureSocket` handshake cannot be cancelled) and wraps the result in its own `Socket`. `HttpServer.listenOn` does not close the gate; `stop()` does.
- The handshake is written by `PreAuthByteLimit.upgrade` (`services/server/pre_auth_byte_limit.dart`), not `WebSocketTransformer.upgrade`: permessage-deflate is never negotiated, frames are capped at 4 KB, a client that sends more than 4 KB before authenticating is dropped, and any client whose message (all its fragments together, read from the frame headers) exceeds 4 KB is dropped (dart:io buffers a whole fragmented message with no total limit). An authenticated phone may send 30 text commands per second; more are ignored, except LEFT_UP, MODE_ARROW and LASER_OFF.
- Pairing QR: `quickremote://HOST:PORT:PIN[:FINGERPRINT]`, built and parsed by `PairingPayload` in the shared package. FINGERPRINT is the base64url SHA-256 of the certificate DER; the server reads its own certificate through a loopback TLS handshake. The client pins a QR fingerprint for that connection (a mismatch is a hard failure, no override). Without one (mDNS or manual entry, no stored pin) it aborts the TLS handshake before sending the PIN and asks the user to compare the security code (`PairingPayload.verificationCode`, the first 64 bits of the fingerprint, shown on the PC dashboard); a later certificate change asks again with the code. An approved fingerprint is pinned for that attempt and stored in SharedPreferences (`cert_fingerprint_<host>`) only after auth succeeds. The client's `HttpClient` has no trusted roots, so the pin is checked even for CA-signed certificates.
- **Text frames** are JSON commands. The server rejects anything not in `RemoteCommands.allowedCommands` or whose `PREFIX:` part is not in `allowedPrefixes` (`SET_PEN_COLOR`, `SET_HIGHLIGHTER_COLOR`, `START_AT`, `VOLUME_SET`). **To add a command, update `remote_commands.dart` first**, then the PC dispatcher and `InputService`. Both apps use the `RemoteCommands` constants and builders (`startAt`, `penColor`, `highlighterColor`, `volumeSet`), never string literals. Commands that only make sense in a running slideshow (drawing modes, ERASE_ALL, BLACK/WHITE_SCREEN) go in `_slideshowOnlyCommands` in `websocket_server.dart`, otherwise they type shortcuts into whatever window has focus. On Windows these shortcuts are also sent only while the slideshow window itself has the focus (`PptController.pressInSlideShow`; the editor does not count, a B there types into the selected text box), which is brought forward first when another window has it, and START_AT jumps with COM `View.GotoSlide` instead of typing the number. When a client disconnects while holding LEFT_DOWN, the server sends LEFT_UP. With several phones connected, the one that started a pointer gesture (MODE_LASER/PEN/HIGHLIGHTER/ERASER … MODE_ARROW) owns the pointer: other phones' pointer commands and move frames are dropped for the rest of their own gesture, and they get a COMMAND_FAILED status. A closed socket or 15 s of silence releases it (`_gestureOwner` in `websocket_server.dart`). A command in `_onePressCommands` (NEXT, PREV, the screen and media toggles) that a different phone repeats within 300 ms is ignored, so two people pressing at once advance one slide. After the first pairing the PC hides the QR code and PIN until the user shows them, and lists connected phones; removing one closes it with code 4005 (the app does not reconnect) and replaces the PIN.
- **Binary frames** (high-frequency mouse movement) are exactly 9 bytes: `uint8 type` (0 = TOUCH, 1 = LASER) + `float32 dx` + `float32 dy`, little-endian. The server coalesces them to ~125 Hz (summed, never dropped: `services/server/move_coalescer.dart`) and ignores LASER frames unless a slideshow is active or the overlay draws the laser. The client splits large deltas into steps of at most ±500, the server's per-frame limit. Encoder: `quick_remote_app/lib/services/websocket/websocket_client.dart`; decoder: `quick_remote_pc/lib/services/websocket_server.dart`.
- **Slide pictures** go the other way, PC → phone, as binary frames too: `SlideImageFrame` (shared package, encoder and decoder): `uint8 magic (0x51)`, `uint8 kind` (0 = current, 1 = next, 2 = thumbnail, 3 = screen: a screen picture where no slide is known, slide and deck 0; phones from before it have three kinds and decode it to null), `uint16 slide` (from 1, 0 only for kind 3), `uint32 deck`, `uint16 width`, `uint16 height`, then the JPEG, little-endian; a short or broken frame decodes to null. The PC sends **no binary frame to a phone that did not send `SLIDE_PREVIEW:1`**: phones from before it read every frame as text and crash. The phone sends `SLIDE_PREVIEW:0/1` (its Ayarlar setting `SettingsProvider.slidePreview`, on by default) after every connect and on change, like `SET_KEEP_INK`, but only to a PC whose `auth` reply carries `previews: true` (the PC knows the feature, whether or not the program on screen can export). `SLIDE_THUMB:n` asks for slide n's thumbnail; both are handled per phone by the server (`CommandRouter.previewSwitch`/`thumbSlide`), never by `InputService`. `SLIDE_STATE` carries `deck`, `SlideImageFrame.deckId` (32-bit FNV-1a) of the platform's `deckKey` (file path and last save time; never sent itself) and the slide count; a new deck empties both sides' caches. A picture that cannot be had is no error: the phone shows the card without one.
- Server → client pushes: `STATUS`, `SLIDE_STATE`, `SMTC_STATE` (now-playing), volume state, `ack`, `auth`, and `OVERLAY` (`overlay`: the auth reply's flag again, when the PC's Laser setting changes or the overlay fails to start; older phones ignore unknown types). These are produced by the polling loop in `services/server/state_broadcaster.dart`.
- A failed command is reported as `STATUS` `COMMAND_FAILED` with a `code` from `RemoteError` (shared package), optional untranslated `info`, and `detail`, a frozen Turkish text for phones from before error codes (`RemoteError.status`). The PC never sends display text: `InputService.onCommandError` takes a `RemoteError`, and the phone turns it into its own language (`RemoteFailure`, `l10n/failure_text.dart`), showing `detail` only for codes it does not know. To add an error, add it to `RemoteError` (with its `legacyDetail`), then to both of the phone's ARB files and `failure_text.dart`.

### PC server (`quick_remote_pc/lib`)

- The window is one screen (`screens/home/home_screen.dart`). Narrow (440×760, the opening size): the status card (`ServerStatusCard`: off, starting, or on with the network's trust and the phone count; amber with a Settings key on a public network), the Linux setup rows (`LinuxSetupPanel`), the pairing card (`PairingCard`: QR beside host, IP and port, PIN and security code below) and the connected phones scroll; the full-width Start/Stop key (`ServerToggleButton`, `server_controls.dart`) stays at the bottom. From 760 px wide the status, setup rows, phones and that key move to a 400 px side pane and the pairing card shows large beside it. Status snackbars float just above that key.
- `ServerProvider` (Provider/ChangeNotifier) owns `WebSocketServer`, which composes `AuthManager`, `NetworkManager` and `StateBroadcaster`. `NetworkManager` handles local IP, TLS cert, network profile and firewall; it is a static facade over `server/network/platform_network.dart` (`windows_network.dart` / `linux_network.dart`).
- Desktop life (`providers/desktop_provider.dart`, `DesktopProvider`, created in `main.dart` with the server provider; pure decisions in `services/desktop/desktop_policy.dart`). One copy at a time: Linux's GtkApplication is unique (no `G_APPLICATION_NON_UNIQUE`; a second launch activates the first, which presents its window), Windows' `main.cpp` holds the mutex `Local\QuickRemotePC` and a second copy shows the first window (`FindWindow` by class and the title "QuickRemote PC") and exits. Tray (`services/desktop/app_tray.dart`, tray_manager 0.8 = nativeapi, a StatusNotifierItem on Linux, no appindicator; builds need GTK 3, X11 and Xi dev files): Show, start/stop the server, phone count, a newer version, Quit; the icon is `BrandTilePainter` drawn at runtime with a status dot (grey off, green on, blue phone connected, amber held back). On Linux the tray is used only when `org.kde.StatusNotifierWatcher` owns its bus name; without a tray closing quits as before. Closing hides to the tray (Settings "Minimize to tray on close", `close_to_tray`, default on; a one-time dialog the first time, `tray_notice_shown`). Settings → Startup and tray also has start at login (`services/desktop/autostart.dart`: `LinuxAutostart` writes `~/.config/autostart/<app id>.desktop` from `DesktopEntry.render(autostart: true)`, only its own marked entry; `WindowsAutostart` the HKCU `Run` value `QuickRemotePC`; both with `--minimized`, which both runners read to keep the window hidden after the first frame, shown anyway when no tray came up), start the server on launch (`start_server_on_launch`, off by default; never on a public network: `heldBack`, an amber row under the status card and in the tray) and the update check (`services/desktop/update_checker.dart`: GitHub `releases/latest` with `HttpClient` at start and every 24 h, compared to `appVersion` from `--dart-define=APP_VERSION`; a "New version: X · Download" row under the status card and a tray item open the release page; never downloads; `check_updates`, default on; `--dart-define=UPDATE_CHECK=false` compiles it out). The window opens hidden only via `--minimized`; `waitUntilReadyToShow` skips `show()` then.
- Everything OS-specific goes through platform interfaces. Shared code must not call PowerShell or shell tools directly.
  - `services/input/input_service.dart` is the interface. `services/input_simulator.dart` is the static facade the rest of the code calls; it picks the implementation by `Platform`. `mouse_controller.dart` is abstracted the same way.
  - `services/input/command_router.dart` parses and validates every command (including `PREFIX:value`) and maps it to `InputService` methods, identically on both platforms. When adding a command, add an `InputService` method and implement it on **both** platforms.
- **Windows** (`services/input/windows/`): win32 FFI (`SendInput`), plus PowerPoint COM, SMTC and volume via PowerShell scripts run by `PowerShellRunner`. That runner keeps two persistent `powershell.exe` processes (started from the absolute System32 path; command and polling), queues jobs, and uses a `___PS_DONE___` sentinel line. In Dart `'''` strings, escape PowerShell `$` as `\$` but never escape a Dart `${...}` interpolation.
- **Linux** (`services/input/linux/`):
  - `uinput_device.dart`: a virtual keyboard/mouse through `/dev/uinput` (FFI `ioctl`). Works on X11 and Wayland. Windows VK codes are mapped in `evdev_keys.dart`.
  - `impress_bridge.dart`: drives a persistent `python3 assets/linux/impress_bridge.py` process (LibreOffice UNO over the pipe `quickremote`, a Unix socket only the user can open; the script refuses the socket if another user owns it) with JSON lines matched by `id`.
  - `pactl_volume.dart` for volume and `mpris_controller.dart` (D-Bus MPRIS) as the SMTC counterpart.
  - `server/network/avahi_publisher.dart` replaces `nsd` for mDNS, since `nsd` has no Linux implementation. mDNS goes through `PlatformNetwork.advertise`/`unadvertise` on both platforms.
  - `services/linux/bluez_hid_repair.dart` registers the `BtHidRepair` RFCOMM service (shared package) as a BlueZ profile over D-Bus (no root; calls are taken only from bluetoothd's bus name) and, when the phone's Bluetooth remote connects to it, makes BlueZ read the phone's SDP records again. BlueZ reads them only when pairing and once per connection the computer starts; `ConnectProfile` with a UUID the phone does not offer is a plain SDP search unless `ServicesResolved` is already set, so then the phone is disconnected and reconnected around it. A refresh adds records, it never removes them. Windows has no counterpart yet.
  - `services/linux/linux_setup.dart` plus `linux_setup_panel.dart` implement the one-time setup: the udev rule via `pkexec`, the LibreOffice `ooSetupConnectionURL` profile entry, and firewalld/ufw ports (a rich rule / `ufw allow from` limited to the local IPv4 subnet, nothing when the subnet is unknown; the firewall check counts such a rule only for the current subnet). Profiles still holding the old `socket,host=localhost,port=2002` entry show as `ImpressStatus.legacyListener` with an update button.
- Impress bridge gotchas:
  - Every UNO call runs on LibreOffice's main thread through `com.sun.star.awt.AsyncCallback`. Calling slideshow APIs from the remote UNO thread deadlocks LibreOffice under the Qt/KDE VCL plugin.
  - The laser, eraser and pen modes use `XSlideShow.setProperty` (`PointerVisible`, `PointerPosition`, `SwitchEraserMode`, `SwitchPenMode`), not `XSlideShowController`.
  - Only the newest waiting `pointer` update is applied, and the running show is cached (looking it up walks every open component, ~20 ms). A queue of pointer updates used to delay the laser and the next mode switch (pen) by seconds.
  - `XPresentation.start()` begins at the slide selected in the editor. START passes `FirstPage` (a custom show uses `start()`), as LibreOffice's F5 does.
  - `XSlideShow.startShapeActivity` is not implemented in LibreOffice. For media control the bridge adds animation triggers to media shapes (click: TOGGLEPAUSE, double click: PLAY then pause), marked with the `quickremote-media` UserData and removed when the show ends, and clicks the shape through `XToolkitRobot` in the `FullScreenPresentation` frame. The slideshow reads a slide's animations when it loads or prefetches the slide, so triggers go to the next few slides ahead of the show; a slide loaded without them is shown again on the first media command (`MEDIA_RELOADED`).
  - A video plays in a native window above the slide, so the laser and ink, drawn on the slide, go behind it. While the laser is over a media shape, the bridge hides it and answers (also to noreply `pointer` updates) with `{"event": "cursor", "x", "y"}` in fractions of the desktop. The server then moves the OS cursor there with the absolute uinput device `UinputDevice.pointer`, and parks it in the show's corner when the laser leaves. The fractions come from the show window's X position and the X root size (X11/XWayland). KWin maps absolute pointer motion to the whole workspace. Ink over videos has no workaround.
  - `setEraseAllInk` needs an `XSlideShow.update()` after it, otherwise the screen keeps the ink until something else repaints.
  - Ink has no transparency (`PenColor` ignores alpha), so from LibreOffice 26.8 (`STROKE_MIN_VERSION`) the highlighter draws a 50 % transparent `PolyLineShape` (Name `quickremote-highlight`) on the slide instead: the `highlighter` reply carries `"strokes": true`, `LinuxInputService.handlesDrawPointer` turns true, the server feeds TOUCH motion as `pointer` updates (the bridge's coalescing keeps every position in `trail`), and LEFT_DOWN/LEFT_UP become `strokeBegin`/`strokeEnd`. Measured on 26.8: a running show draws a change to the slide on screen at once, but by showing the slide again from its start (~150 ms). Its transition plays again, so the bridge switches it off until the show ends. Its animations restart, so slides with animations or media keep the ink. A move during the redraw is lost, so NEXT/PREV/START_AT wait for it (`settle`), and a slide's shapes are removed only after the show has left it (`_erase_left`, run from `state`). Changes to other slides do not redraw. All shapes and transitions are restored at the show's end, the modified flag is reset, and the undo manager is locked while the bridge edits. The eraser does not erase these shapes; ERASE_ALL does.
  - LibreOffice keeps a slide's ink and shows it again when the show returns to the slide. Unless the phone that sent the command keeps it, the bridge erases the ink before every NEXT, PREV and jump (`"clearInk"` in the request). The setting lives on the phone (`SettingsProvider.keepInkOnSlideChange`, the Ayarlar screen): `WebSocketService` sends `SET_KEEP_INK:0/1` after every connect and on change; the server keeps it per socket (`_keepInk` in `websocket_server.dart`, in memory) and passes that phone's value as `keepInk` to `slideNext`/`slidePrev`/`slideStart`/`slideStartAt` (`CommandRouter.execute`); a phone that never sent one gets the ink erased. On Windows erasing presses E (PowerPoint) or calls COM `EraseDrawing` (WPS) before PageDown/PageUp, but only when the slideshow window has the focus.
  - Presentation commands fall back to key presses when no Impress slideshow is reachable.
- WPS Presentation (both platforms):
  - Windows: every COM script starts with `PresenterCom.lookup` (`input/windows/presenter_com.dart`), which sets `$ppt` to PowerPoint or WPS (`KWPP.Application`, or `PowerPoint.Application` when WPS stands in for Office), preferring the one with a running show, and `$qrPresenter`. WPS reports `Name` "Microsoft PowerPoint" (Version 12.0), so its `Path` tells it apart. The slide-state poll caches it in `PresenterCom.active`. WPS gets pointer modes through COM `View.PointerType` (its Ctrl+L moves the show, Ctrl+E is not the eraser), its laser pen with Ctrl+A then Ctrl+R in the focused show (`PptController.wpsLaser`; 150 ms apart, WPS 12.1 drops a Ctrl+R that follows Ctrl+A at once; only Ctrl+A puts it away, also before the next mode), erase-all and ink clearing through `EraseDrawing`. Verified on WPS 12.2.0.23196 (Windows): GotoSlide, `View.State` black/white, B/W keys, Ctrl+I highlighter, `PointerColor.RGB`, F5.
  - Windows windows (measured, PowerPoint 365 16.0.20430 and WPS 12.2): the PowerPoint show is a `screenClass` window of POWERPNT.EXE; WPS runs its editor in `wps.exe` (`PP12FrameClass`) and the show in a `Qt5QWindowIcon` window of `wpp.exe`. COM gives no window handle (`SlideShowWindow.HWND` is missing in PowerPoint 365, empty in WPS), so `PptController._findShowWindow` enumerates windows. With the pen or another tool on, the first Esc only puts the tool away, so END presses Esc until the show window is gone (at most 3), then answers the "keep ink annotations?" prompt with Discard (Tab, Enter): `NUIDialog` in PowerPoint, `#32770 (Dialog)` of `wpp.exe` in WPS. COM `View.Exit()` blocks on that prompt; never use it.
  - Media on Windows: PowerPoint's COM `View.Player` works (State 0 playing, 1 paused, 2 stopped). ### Local log and problem reports (both apps)

- `AppLog` (shared package, `src/app_log.dart`) writes every line to the console and to `logs/quickremote.log` under the app support dir (phone: the app's own files dir), rotated at 1 MB, 3 files kept. Lines are queued and written in batches every 500 ms (at most 5000 queued, 4000 chars a line), so logging never waits for the disk. Nothing is ever uploaded; there is no remote crash reporting (decided, docs/raporlar/ALTYAPI_RAPOR.md item 6).
- `main()` of both apps calls `installAppLog` (`lib/services/app_log_setup.dart`, the same in both): it reassigns Flutter's global `debugPrint` to `AppLog.log` (call sites keep using `debugPrint`; the Linux bridges' stderr already goes through it in `ScriptBridge`) and logs uncaught errors from `FlutterError.onError`, `PlatformDispatcher.instance.onError` and an `Isolate.current` error listener (no `runZonedGuarded`). Native crashes (FFI segfaults) are not caught. Tests never call `main()`, so there `debugPrint` is Flutter's own.
- `AppLog.redact` cleans every line before it is printed or written: PINs (any lone 6-digit number), `quickremote://` contents, certificate fingerprints (hex, colon hex, base64url) and security codes, notes and media titles (`notes`, `title`, `artist`, `deckKey`, `path`, `pin`, `auth`, `fingerprint` … values in JSON, Python and Dart map text), file paths (Unix, Windows, UNC, `file:` URLs, the home folder; system folders such as `/dev/` stay). IP addresses, ports and device names stay. `test/app_log_test.dart` in the shared package guards it: a new kind of private data in a log line needs a rule and a test there.
- PC: Settings → Sorun giderme (`settings_dialog.dart`, `services/desktop/problem_report.dart`): "Günlüğü dışa aktar" saves the logs with a version/platform header through `file_selector`'s save dialog, "Sorun bildir" opens `AppLog.issueUrl` (a new GitHub issue with the version from `app_version.dart`, platform and programs) with `openInBrowser`. The phone: Ayarlar → Yardım (`settings_screen.dart`, `services/problem_report.dart`): "Hata günlüğünü paylaş" writes the logs to a temp file and opens Android's share sheet (`share_plus`), "Sorun bildir" opens the issue with `url_launcher` (version from `lib/app_version.dart`, `--dart-define=APP_VERSION`, PC programs, Bluetooth target). ### Mobile client (`quick_remote_app/lib`)

- State uses Provider: `WebSocketService`, `SettingsProvider` and `DiscoveryService` are registered in `main.dart`. `WebSocketService` is a facade over `websocket/websocket_client.dart` (transport, TLS and pinning), `presentation_state.dart` (slide/media state) and `analytics_tracker.dart` (per-slide timing for analytics reports).
- There are two independent control modes:
  - **Wi-Fi mode**: `screens/remote/` talks to the PC server.
  - **Bluetooth HID mode**: `screens/bt_remote/` makes the phone act as a Bluetooth keyboard and mouse, so no PC app is needed. `services/bluetooth/bt_hid_service.dart` bridges over the `com.quickremote.quick_remote_app/bt_hid` MethodChannel and the `bt_hid_events` EventChannel to the native `android/.../BluetoothHidService.kt` (`BluetoothHidDevice` API). `bt_key_mapping.dart` maps commands to HID key/consumer reports per `BtTarget` (user-selected PowerPoint, Impress or WPS, stored in `SettingsProvider`). Impress's slideshow has no keyboard shortcut for laser, highlighter or eraser, so those are no-ops; WPS has Ctrl+I for the highlighter and Ctrl+R for its laser pen (sent after Ctrl+A, so it comes on whatever was on), and Ctrl+E for its eraser (`ShowErase` in the show's shortcuts, verified on WPS 11.1; on Windows WPS 12.2 it did something else, where COM sets the eraser). A left click without the pen advances the slide, so the BT toolbar hides the tools without a key.
    - The HID SDP record exists only while a BT screen is open. A computer paired with the phone without it (e.g. earlier, for audio) refuses the keyboard (BlueZ: `Could not parse HID SDP record`, `unknown device`), and only the computer can read the records again. `BluetoothHidService.kt` counts a link that fails or drops within 3 s as refused and connects once to the PC's `BtHidRepair` service (`refreshing`); without one it reports `host_unaware`, and the connect screen shows `BtHostSetupView` while it keeps retrying (every 8 s at most), so the remote opens once the user has reconnected (Linux) or re-paired (Windows) the phone.
    - Android drops the HID registration of an app that leaves the foreground without a foreground service, and `registerApp` fails in the background or while another app holds the HID profile (`error:hid_unavailable`). So the connect screen holds a `BackgroundSession` as well, acquired before registering (its permission dialogs put the app in the background), and registers again on resume (`BtHidService.ensureConnected`). A second `registerApp` while one is pending is refused just like that ("another app is registered"; the permission dialog's resume caused it), so `BluetoothHidService.kt` never registers or asks for the profile proxy twice (`registering`, `proxyRequested`). Bluetooth switched off is no error: the service reports `bluetooth_off` (`BtHidConnectionState.bluetoothOff`, the connect screen's `BtOffView` with `ACTION_REQUEST_ENABLE`, a snackbar on the remote), releases the profile, and starts again by itself on `ACTION_STATE_CHANGED` ON. The phone is visible to a computer searching for devices only while Android's Bluetooth settings are open or after `BtMakeVisibleButton` (`ACTION_REQUEST_DISCOVERABLE`, needs `BLUETOOTH_ADVERTISE`). The native side reports the computer it tries (`target:<name>`), shown instead of "waiting for pairing".
- The home screen keeps the last five PCs (`DeviceHistoryRepository`, with their PINs). A PC found over mDNS that is one of them (same host and port) connects with the saved PIN; the PIN dialog opens only when there is none or the PC answers wrong PIN.
- `services/wear/wear_bridge.dart` (`WearBridge`, created in `main.dart`) is the watch app's way to the PC; see "Watch app".
- Slide pictures (see the PC section): `WebSocketClient` decodes binary frames with `SlideImageFrame` (`onImage`); `PresentationState` keeps a few large and medium pictures and up to 200 thumbnails of the current deck; `WebSocketService` exposes `currentSlideImage` (the large one, else the "next" one sent before NEXT, so it shows at once), `nextSlideImage`, `thumbnail(n)`, `screenImage` (the last kind-3 picture, shown only while a viewer is in front without a show or a show runs with no slide number; dropped when another kind of window comes to the front, kept across the empty SLIDE_STATE) and `previewsAvailable` (`previews` in the auth reply and the setting on). The thumbnail requests (`services/websocket/thumbnail_requests.dart`) go four at a time in the order the list asked; a cell scrolled away takes back its unsent request, and one not answered in 4 s counts as failed (empty frame, not asked again for that deck).
  - With a `screenImage`, `SlideCard` shows it in the picture's place (`SlideCard.showsScreen`, label `screenPreviewLabel`) and the presenter view shows it large with only Previous/Next (no number, next slide or notes).
  - `SlideCard` (`views/main_controls_view.dart`) shows the picture (`widgets/slide_image.dart`, `SlideImage`: 16:9, a black or white cover while that screen is on) right of the slide number once the deck has one (`SlideCard.showsPreview`); otherwise the card is as without previews.
  - Tapping it, or the note preview while it shows, opens the presenter view (`screens/remote/presenter_view_screen.dart`): the slide large, the next one, the notes, Previous/Next; upright stacked, on its side the slide left and the rest right. It is pushed over `RemoteScreen`, which keeps the volume keys, the background session and the timer; a lost link leaves the last state faded.
  - "Go to slide" (`utils/go_to_slide_sheet.dart`) shows a thumbnail grid instead of the number keyboard while a show runs and the deck has a picture (so a program that cannot export never shows skeletons).
- `front` and `caps` (`PresenterCaps`, shared package): `PresentationState.caps` takes them from every SLIDE_STATE and from the "no show" STATUS (the empty SLIDE_STATE after it keeps them), `WebSocketService.presenterCaps`/`frontWindow` expose them. `ShowInfo` (`screens/remote/utils/show_info.dart`) is the one place the screens ask what works (`tool(DrawTool)`, `eraseAll`, `blank`, `media`, `rewind`, `canJump`, `colorsAvailable`, `notes`, `previews`, `spotlight`, `zoom`, `undo`): from `caps` when the PC sends them, else the old guesses from `presenter`, `platform` and `current: 0`. A tool missing from `caps` is faded (`DrawToolBar.available`, `clearEnabled`). With a PDF viewer or a browser in front and no show (`ShowInfo.viewer`) the red "no presentation" alert becomes an info line (`viewerInFront`), Start becomes "Full screen" (still START) and Go to slide is hidden. The watch does not get `front` yet.
- App shortcuts and the Quick Settings tile (`LaunchLink.kt`, `QuickTileService.kt`, `res/xml/shortcuts.xml`; texts in `res/values` and `res/values-tr`): static shortcuts "Bluetooth remote" and "Scan QR", a dynamic "Connect: <last PC>" (`ShortcutManager`), and a tile that connects to the last PC (active while connected over Wi-Fi, the last PC's name as subtitle on Android 10+; not an active tile, so a killed app never leaves it on). They open `MainActivity` with `quickremote://connect/last`, `quickremote://bluetooth` or `quickremote://scan`, only as explicit intents (shortcuts go through the non-exported `ShortcutActivity` in its own task, so the launcher's CLEAR_TASK does not end a running remote; no intent filter). Dart reads them over the `…/launch` channel (`services/launch_actions.dart`, `LaunchActions`, handled by `HomeScreen`) and tells the native side the first recent PC's name and the connection state. `LastPcConnect` connects to the first recent PC with its saved PIN; when its address does not answer it looks for its name over mDNS (6 s) and connects there with the certificate pinned for the old address, so another PC under that name fails (`certRejected`) before the PIN; else the home screen says the PC was not found. Recent PCs are saved under their mDNS name, else the `auth` reply's `name`, else the address. `bluetooth` opens the Bluetooth connect screen (last `btTarget`). The home-screen widget is not done.
- Hardware volume keys are captured natively in `MainActivity.kt` and exposed through the `.../volume_keys` MethodChannel (`screens/remote/utils/hardware_key_handler.dart`).
- `flutter_background` keeps the connection alive when the app is in the background or the phone is locked, but only while a remote screen (Wi-Fi or Bluetooth) or the Bluetooth connect screen is open: `services/background_session.dart` enables it on open and disables it on close. The plugin does not declare its `IsolateHolderService`, so the app manifest does, with `foregroundServiceType="connectedDevice"` and `FOREGROUND_SERVICE_CONNECTED_DEVICE` (required on Android 14+; its runtime prerequisite is covered by `CHANGE_WIFI_MULTICAST_STATE`).

### Watch app (`quick_remote_wear`)

- The watch never talks to the PC. It talks to the phone app over the Wearable Data Layer (`play-services-wearable`), and the phone passes its commands on over whichever connection it has: `watch ⇄ phone ⇄ PC`. Over Wi-Fi the PC sees one client, the phone; nothing in `quick_remote_pc` or the shared package knows about the watch. The watch pairs with nothing. The earlier direct Bluetooth HID mode (the watch as a keyboard for the PC) was removed on 2026-10-13: its pairing with the PC broke in ways the app could not repair.
- While the phone has no Wi-Fi connection but is the computer's Bluetooth keyboard (`BtHidService`, the `bt_remote` mode), `WearBridge` sends the watch's commands as that mode's keys (`BtKeyMapping.forCommand` with `SettingsProvider.btTarget`) and the laser's movement as mouse reports (half the Wi-Fi units, in steps of ±127). The state then carries `mode: bluetooth`: a keyboard gets no answer, so the watch shows "Bluetooth" in place of the slide number and gets no errors, and its laser is the picked program's shortcut (none in Impress: the cursor). Wi-Fi comes first when both are connected.
- The Data Layer joins only apps with the same `applicationId` and signing key, so the watch app's `applicationId` is the phone's (`com.quickremote.quick_remote_app`; namespace `com.quickremote.wear`) and its release signing reads the phone's `key.properties`; without that file both fall back to the debug key, which also matches. Install both with the same key when testing. Its `versionCode` is 1 000 000 + the phone's (one Play listing). `com.google.android.wearable.standalone` is `false`.
- The words of the link are in `phone/WearProtocol.kt` (watch), `WearRelay.kt` (phone, native) and `wear_bridge.dart` (phone, Dart). `WearProtocolTest` and `WireCommandsTest` in the watch project read the phone's files and `remote_commands.dart` and fail when they differ.
  - The phone declares the capability `quickremote_phone` (`res/values/wear.xml`); the watch sends to the reachable node that has it (`CapabilityClient`). No such node is "phone not reachable".
  - State is one DataItem, `/quickremote/state` (`link`: `closed`/`disconnected`/`connecting`/`connected`, `mode`: `wifi`/`bluetooth`, `pc`, `running`, `laserAnywhere` (the PC's overlay draws the laser: `ConnectedScreen`'s `canPoint` keeps the laser on without a show, black/white stay faded), `current`, `total`, `pointer`: `laser` (`arrow`, which phones sent for Windows WPS before its laser pen was used, is still understood), or `cursor` for Impress over Bluetooth, so that the watch names it; and the talk's clock, see below), written urgent by the phone: a last value, which the system syncs again after the two were apart. Commands (`/quickremote/command`, a `RemoteCommands` name), laser movement (`/quickremote/move`, two little-endian float32) and PC errors to the watch (`/quickremote/error`, text) are messages (`MessageClient`): sent now or not at all.
  - The DataItem can be stale (the phone app was killed while "connected"). The watch sends `/quickremote/hello` on every start and when the phone comes into reach, and shows the stored state only until the answer; every hello is answered with a fresh write (a `stamp` makes an unchanged state a change). Two unanswered hellos (3 s apart) count as no phone.
- Phone side: the manifest's `WearListenerService` receives the messages, also while the app is closed (Google Play services binds to it). The connection to the PC lives in Dart and the Flutter engine exists only while the app runs, so `WearRelay` hands a message to `WearBridge` over the `…/wear` MethodChannel when `MainActivity` has attached one, and otherwise drops it and writes the state `closed`; `MainActivity.onDestroy` writes `closed` too. The watch then says "open QuickRemote on the phone", with a button that opens it (`RemoteActivityHelper`, the `quickremote://watch` VIEW filter on `MainActivity`; `flutter_deeplinking_enabled` is `false` so that Flutter does not take the link for a route). Opening the app does not connect it to a PC; the user does that on the phone.
- The laser's own Bluetooth socket (`WearDirect.kt` on the phone, `DirectLink.kt` on the watch) needs "nearby devices" (`BLUETOOTH_CONNECT`) on both. The phone asks for it once per run when a watch first says hello (`WearBridge._openDirectLink`, then `startDirect` on the channel); without it the laser goes over the Data Layer and lags (a phone used only over Wi-Fi never had it before 2026-10-19).
- `WearBridge` writes nothing until a watch has asked (most phones have none; `WearRelay.attach` counts a connected Wear node as having asked). It accepts only `watchCommands` (NEXT, PREV, START, END, BLACK_SCREEN, WHITE_SCREEN, MODE_LASER, LASER_OFF, MODE_ARROW) and sends them with `WebSocketService.sendCommand`. A `RemoteFailure` within 3 s of a watch command goes to the watch as text in the phone's language (`WearBridge.failureText`, set in `MaterialApp.builder` like `BackgroundSession.notificationText`); the watch holds no error texts. The PC's name is `WebSocketService.pcName` (from the `auth` reply); for a PC from before that, its mDNS name when discovery found it, else its address.
- The talk's clock: the talk's length (`SettingsProvider.talkDuration`, the state's `duration`) is picked on the watch's Start page (`/quickremote/duration`) or with the phone's presentation timer, and either side takes the other's. `WearBridge` keeps the clock the watch shows (`timerTarget`, `timerRunning`, `timerStart` in ms since the epoch, `timerElapsed` while paused): the remote screen's `PresentationTimerController` while it runs or is paused (`attachTimer`), otherwise one of its own from the show's start to its end (over Bluetooth from the watch's START to its END). Its warnings (the timer settings' times and patterns) go to the watch as `/quickremote/alert` messages (`warning:300:double`, `timeUp:0:triple`, an empty pattern does not vibrate), which the watch's manifest `AlertService` vibrates (alarm usage) also while the remote is not on screen; `WearProtocolTest` checks the patterns against `vibrateTimerPattern`. The phone's own timer still vibrates the phone.
- The connection survives a locked phone only while the phone's remote screen (Wi-Fi or Bluetooth) is open (`BackgroundSession`), as for the phone itself.
- Laser: the watch's laser screen is a touchpad. Finger down sends MODE_LASER, movement goes as `move` messages which the bridge sends as LASER frames (split to the PC's ±500), finger up sends LASER_OFF and MODE_ARROW, as the phone's touchpad does. `MoveSender` keeps at most 4 movements on their way and sums what comes in meanwhile, so a slow link makes larger steps, not a queue: a movement counts as arrived when the phone has answered it (`/quickremote/moved`, sent by `WearRelay` on receipt; 500 ms without it counts as lost), at most 40 a second. Waiting for each answer gave one movement per round trip, 15 a second. The `sendMessage` Task is no measure: it completes when the message is queued, and movement queued faster than the link carried it arrived seconds late. A finger held still sends an empty movement every second; the bridge puts the laser away after 3 s of silence (watch out of reach) and turns it on again when movement arrives without MODE_LASER. While the laser screen is open the watch pings the phone five times a second (`PhoneLink.laserScreen`), since an idle link starts slow. Measured on a Galaxy Watch 6 and S23 FE: 26 to 31 movements a second reach the phone, with two or three gaps over 80 ms a second, which show as a slight stutter. To measure the link: `adb shell setprop log.tag.QuickRemoteLink DEBUG` on the watch, then `adb logcat -s QuickRemoteLink` logs each ping's round trip while the finger is down, and the message rate per gesture. Wireless adb on the watch itself slows the link (round trips of 90 to 300 ms, half the rate): judge the laser with it off, from the phone's log (`adb shell setprop log.tag.BluetoothHidService VERBOSE` logs every mouse report in Bluetooth mode).
- Watch code: `phone/` (`PhoneLink`: the three Data Layer clients, state and events as flows; `PhoneState`; `MoveSender`), `remote/` (`RemoteAction`, `WireCommands`, `BezelStepper`: one step per bezel detent, summed crown deltas), `ui/` (`WearApp`: navigation, the time on top (without the PC's name, which only the ambient screen shows), the error banner; `PhoneStatusScreen`; `ConnectedScreen`: the pages `StartPage` (only while no show runs; Start stays on it until the show is known to run, then the slide buttons come, and after 8 s without one it says the show did not start; a show that ends returns to it; − and + under Start pick the talk's length), `ToolsPage` (four quarters: laser, white, black, and END, which takes a 1 s hold) and `RemotePage` (a large Next filling the lower half, small Previous and laser buttons, slide progress along the upper edge (a dot per slide, as the phone's segmented bar: passed in the theme's color, the current one the laser's; a plain arc past 40 slides, `slideDots`), the talk's clock with the timer symbol (time left, past the end "+1:12" in red, without a length the time run; from a phone that tells none, counted on the watch); Next held for 350 ms turns into the laser until the finger lifts, and says so under its word until that has been done once, `Tips`). Over Wi-Fi with no show running (also a PDF) the PC ignores the laser and black/white, so `ConnectedScreen` fades them and a tap says "only while a slideshow runs"; over Bluetooth nothing is known and they stay on. Start is green in every theme, as on the phone; `BlankScreen`, shown after the watch sent BLACK_SCREEN or WHITE_SCREEN, since the PC reports neither, until sent again or the slide changes; `LaserScreen`; `AmbientScreen`). While the slide buttons are on screen (and the screen is not dimmed) `WearApp` keeps the phone link awake as the open laser screen does (`PhoneLink.laserScreen`), so the held laser is as quick. Type is the phone's (`WearFonts`: Inter for text, Space Grotesk for figures and titles, in `res/font`, their licenses in `assets/licenses`). Colors come from `WearTheme` (`ui/theme/Theme.kt`: Cobalt, the default, OLED, high contrast, mint, violet: the phone design's themes but its light-only Sunset), read through `LocalWearPalette` and stored under `theme`. The watch has no picker: the phone's Tema screen has "Use on the watch too" (`SettingsProvider.watchUsesTheme`, on by default), and while it is on `WearBridge` writes the state's `theme` (`WearBridge.watchThemeOf`: Sunset, light only, as `cobalt`, said under the switch); `PhoneLink` stores a new one with `WearTheme.store` and applies it at once. Without the field the watch keeps the theme it has. `PhoneLink` runs between `MainActivity.onStart` and `onStop`, and while the phone is connected to a computer also in `PresentingService` (its `start`/`stop` are counted): a `connectedDevice` foreground service whose notification is an Ongoing Activity, so that the watch (Wear OS 5+) shows the remote again when the screen wakes instead of the watch face. Not only while a show runs: over Bluetooth the watch cannot tell (it counts the talk's clock, run from its own Start, as a running show). It stops by itself 60 s after the connection went. Measured on a Galaxy Watch 6 (Wear OS 6): without it the watch face comes back after the screen was off 20 s (Samsung's `setting_show_last_app_within_time`), with it the remote; without the notification permission it does not work. The app asks for the notification permission (Android 13+) and "nearby devices" (the laser's socket) once per start. Texts are in `res/values` (English, the fallback) and `res/values-tr`; change both.
